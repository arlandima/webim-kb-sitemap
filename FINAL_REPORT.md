# FINAL REPORT — Webim AI Knowledge

Ветка: `claude/webim-ai-knowledge-fx8wti` · Итог: **работающий прототип end-to-end**, индекс реальной Базы знаний в репозитории, запуск одной командой.

## Что построено

Независимый поисково-ответный слой над публичной Базой знаний Webim: краулер → парсер → секционные чанки с provenance → SQLite (FTS5 + векторы) → гибридный поиск + реранкер → ответ по источникам (LLM или извлекающий) → интерфейс в стиле Webim. Сайт webim.ru и KB не изменялись; краулер читает только `/kb/`.

Реализовано (всё запускалось и проверялось): краулер с кэшем и условными запросами; парсер MkDocs; секционное разбиение с якорями; инкрементальная синхронизация; гибридный поиск (лексика + семантика чанков + семантика заголовков → RRF → реранкер); отказ при недостатке доказательств и при неизвестных названиях; провайдеры LLM (OpenAI-совместимый, Anthropic) со стримингом; режим без LLM; фильтр «Искать в»; UI: главная, результаты, источники, инспектор источников, релевантные статьи, уточняющие вопросы, обзор документации, `/demo`, `/admin`; тесты; оценка поиска; документация.

**Частично:** уточняющие вопросы (контекст только для поиска и промпта, без переписывания запроса моделью); ночная синхронизация (команда и инструкция есть, планировщика и горячей перезагрузки индекса нет).
**Не проверялось:** работа с реальной LLM (только имитационный OpenAI-совместимый сервер в тестах), GPU-ускорение ONNX, Windows/macOS-запуск (код кроссплатформенный, но запускался только на Linux).

## Архитектура

См. `docs/ARCHITECTURE.md`. Один Python-процесс (FastAPI), один файл SQLite, эмбеддинги/реранкер на ONNX Runtime (без PyTorch), статический интерфейс без сборки. Выбор упрощает запуск (одна команда, без Docker/сервисов) и переносимость Windows/macOS.

* Найдено и проиндексировано: **339 статей** (327 + 12 страниц-оглавлений, найденных по ссылкам), **4 883 чанка**, ошибок загрузки **0**, дубликатов содержимого пропущено 1.
* Эмбеддинги: 4 883 чанка (`multilingual-e5-large`) + 4 163 уникальных заголовка.
* Целостность provenance: у всех 4 883 чанков якорь найден в HTML страницы (`eval/check_links.py`); URL 10 демо-страниц отвечают 200 на живом сайте, якоря присутствуют.
* Первый прогон: краулинг 248 с (778 запросов, включая ≈ 430 лишних запросов к картинкам из-за найденной и исправленной ошибки канонизации; исправление и негативный кэш 404 теперь исключают их). Повторная синхронизация без изменений: **1 запрос, 1,3 с**.

## Поиск

* **Лексика:** SQLite FTS5, BM25 (веса заголовок 6 / путь 4 / текст 1) по Snowball-стеммам ru/en; идентификаторы (`password_hashers`, `webimsdk.onBan`, camelCase) индексируются целиком и по частям.
* **Семантика:** `multilingual-e5-large` (1024-мерные, ONNX/CPU), матрица в памяти; отдельные эмбеддинги «Статья › Раздел».
* **Слияние:** RRF (k = 60), три списка. **Реранкер:** `bge-reranker-v2-m3` int8, 20 кандидатов (не более 3 чанков на статью в пуле — чтобы справочники SDK не вытесняли остальное).
* **Отказ:** порог реранкера 0,12 (или 0,05 при независимом подтверждении) + правило «неизвестное название» (Bitrix24, Signal).

## ИИ

* Провайдеры: `OpenAICompatible` (vLLM, SGLang, LM Studio, Ollama…), `AnthropicProvider`, «без LLM». Настройка через `.env`.
* Grounding: системный промпт «документация — данные», блоки `<source>` с очищенным текстом, проверка цитат, отказ модели трактуется как отказ, при низкой уверенности LLM не вызывается.
* Без LLM: извлекающий ответ — предложения дословно из найденных фрагментов со ссылками `[n]`.

## Интерфейс

Веб-интерфейс на вкладках: Спросить / Документация / Примеры + служебная `/admin`. Дизайн выведен из webim.ru: градиент `#313098 → #4ac7e3`, бирюзовые пилюли `#0d7791`, тёмно-синий `#14284d`, Roboto (те же файлы шрифтов, что у KB), официальный логотип Webim без изменений. Состояния: загрузка (скелетон + статус), ошибка (с повтором), «недостаточно информации», пустое оглавление/статья не найдена. Доступность: skip-link, видимые фокусы, `aria-live` ответа, диалог инспектора закрывается Esc, `prefers-reduced-motion`, кнопки ≥ 36 px.

## Оценка поиска (`eval/questions.json`, 46 вопросов; `eval/results.json`)

40 вопросов с ожидаемой статьёй (простые, перефразированные, размытые, технические, точные термины, смешанный ru/en, «много статей») + 6 без ответа в KB.

| Режим | hit@1 | hit@3 | hit@5 | MRR | верные отказы | ложные отказы |
|---|---|---|---|---|---|---|
| Только лексика (BM25) | 55 % | 72 % | 85 % | 0,665 | 6/6 | 6/40 |
| Гибрид (лексика + семантика, RRF) | 72 % | 88 % | 92 % | 0,802 | 5/6 | 0/40 |
| **Гибрид + реранкер (продукт)** | **85 %** | **95 %** | **98 %** | **0,902** | **6/6** | 1/40 |

Оговорки — важно: набор составлен мной по реальным статьям **до** запуска, но затем я использовал его, чтобы выбирать компоненты и пороги (сигнал по заголовкам, лимит чанков на статью, порог отказа, правило неизвестных названий), и расширил ожидаемый список для одного вопроса после чтения статьи (V2). Цифры поэтому оптимистичны; независимого теста нет. Полностью не решён вопрос «как передать чат другому оператору» (S4): нужная статья называется «Переадресация диалога», выше оказываются другие. На 16 «свежих» вопросах вне набора (ручной просмотр) почти все ответы были по делу; слабые места: «как настроить приветствие в чате» и «как сменить язык интерфейса» находят справочники SDK/инструкцию про язык браузера; «есть ли мобильное приложение для оператора» — SDK вместо приложений оператора (в последнем случае помогает фильтр «Искать в: Приложения»).

Задержка (4 vCPU, без GPU): лексика единицы–десятки мс, эмбеддинг запроса ≈ 80 мс, семантика ≈ 90 мс, **реранкер ≈ 2,5 с**, итого ≈ 2,6–2,8 с.

## Три взгляда

**A. CEO Webim.** *Понятна ли ценность за 60 секунд?* Да: заголовок «Спросите что угодно о Webim», клик по вопросу-карточке → ответ + источник + «Открыть оригинал» на нужный раздел; блок «Почему это нашлось» объясняет разницу формулировок. *Достаточно ли достоверно выглядит?* Визуально да (фирменные цвета, логотип, шрифт). *Очевидно ли улучшение?* На перефразированных вопросах — да. Замечания: без подключённой LLM ответ — «выдержки», а не связный пересказ (честно подписано; для демо стоит подключить локальную модель до показа); ≈ 2,6 с ожидания на CPU; «Открыть оригинал» требует интернета. Исправлено по итогам: нерелевантные хвосты в ответе (отбор доказательств), шумные списки, обрезанный текст на мобильном.

**B. Клиент Webim.** *Быстрее ли, чем искать по разделам?* Да для «человеческих» формулировок (паузa, заметка, «сначала вопрос»). *Можно ли доверять?* Ответ только из документации, отказ при отсутствии информации, названия вне документации не «подгоняются». *Можно ли проверить?* Инспектор показывает точный фрагмент и URL. *Дойти до оригинала?* Да, с якорем на раздел. Остаётся: общие короткие вопросы могут дать не тот раздел (добавлен фильтр «Искать в»), якоря MkDocs (`#_2`) сами по себе нестабильны при правках статей.

**C. Старший инженер.** *Это реальная система поиска/RAG?* Да: собственный краулер, FTS5-индекс, векторы, RRF, кросс-энкодер, оценка с метриками. *Provenance настоящий?* Да, хранится в каждом чанке и сквозь весь пайплайн; целостность якорей проверяется скриптом. *Цитаты из индекса?* Извлекающие — дословно из чанков; LLM-цитаты проверяются на существование номера (но не «дословность» — семантическую верность модель не проверяем). *Синхронизация настоящая?* Да, покрыта тестами (новые/изменённые/удалённые/сбой/пересборка), эмбеддинги кэшируются по тексту. *Провайдер заменяем?* Да (OpenAI-совместимый/Anthropic/нет; реестры эмбеддингов и реранкеров). *Сопровождаемость?* 62 теста, ~2 000 строк Python, без фреймворков во фронтенде. Риски: матрица эмбеддингов в памяти и SQLite (для десятков тысяч чанков ок, для продукта — векторное хранилище); пороги откалиброваны на маленьком наборе, написанном разработчиком; нет rate-limit/аутентификации; `Retriever.reload()` не вызывается автоматически после синхронизации; нет автотеста «реальная LLM».

## Известные ограничения (кратко)

1. Реальная LLM не проверена; GPU-провайдеры ONNX не проверены; Windows/macOS не запускались.
2. Оценка небольшая и не независимая (см. выше).
3. Реранкер на CPU ≈ 2,5 с; первый запуск скачивает ≈ 2,8 ГБ моделей.
4. Нет аутентификации/лимитов — не выставлять в интернет.
5. Изображения из статей не индексируются и в читалке не показываются (только подписи).
6. Неоднозначные короткие вопросы могут вернуть справочник SDK вместо инструкции для оператора.
7. Индекс в Git (~60 МБ бинарный файл): при каждом обновлении коммит будет тяжёлым — для продукта индекс держать вне Git.

## Рекомендуемые следующие шаги

1. Подключить локальную LLM (LM Studio / vLLM), снять качество и скорость; при необходимости подобрать модель (`scripts/check_llm.py`).
2. Собрать независимый тест-набор из реальных вопросов поддержки (150+) и перекалибровать пороги.
3. Ускорить реранкер (GPU) и добавить автоперезагрузку индекса после ночной синхронизации + планировщик.
4. Журнал вопросов без ответа и «помог / не помог» — источник улучшений документации.
5. Пилот на документации одного клиента (свой источник + оценка уверенности + передача оператору) — см. `docs/ROADMAP.md`.
