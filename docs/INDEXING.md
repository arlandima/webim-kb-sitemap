# Индексация и синхронизация

## Что найдено на сайте

* Webim KB — статический сайт на **MkDocs Material** (`generator: mkdocs-1.6.1, mkdocs-material-9.7.7`). Каждая статья — отдельный HTML, `<link rel="canonical">`, `<article class="md-content__inner">`, заголовки с `id`, дата обновления в `.git-revision-date-localized-plugin-date`.
* Живой `https://webim.ru/kb/sitemap.xml` — **327 URL** с `lastmod`. `robots.txt` не запрещает `/kb/`.
* Файлы `kb_sitemap.xml` и `kb_sitemap_1.xml` в этом репозитории **устарели** (февраль 2026): из 350 URL 97 больше не существуют/переехали, 74 новых страниц в них нет. Они используются только как запасной вариант, если живой sitemap недоступен.
* 12 страниц-оглавлений (`/kb/apps/`, `/kb/devops/` …) в sitemap нет — они находятся по ссылкам внутри статей.
* Итог первого прогона: **339 статей**, **4 883 чанка**, 0 ошибок, 1 дубликат содержимого пропущен, 778 запросов, 248 с при паузе 0,3 с.

## Как работает краулер

* Область: только `https://webim.ru/kb/…`. `canonicalize()` отбрасывает другие хосты, `?query`, картинки/CSS/JS, `..`-выходы; редиректы обрабатываются вручную, каждый шаг проверяется на область.
* Пауза между запросами 0,3 с (`CRAWL_DELAY`), 3 повтора с экспоненциальной паузой при 429/5xx, идентифицируемый User-Agent.
* Кэш страниц `data/cache/pages/` (не в Git): `ETag`/`Last-Modified` → условный GET (304 = без загрузки). 404 кэшируются на 7 дней.
* Скрипты и код со страниц не исполняются: парсер работает с HTML как с данными (BeautifulSoup), `script/style/nav/svg/iframe/form` отбрасываются.

## Алгоритм `python -m webim_ai.sync`

1. Обнаружение: sitemap + ссылки из статей (в пределах `/kb/`).
2. Если у страницы тот же `lastmod`, что в индексе, и есть кэш — **пропуск без запроса** (`--full-check` отключает эту оптимизацию, `--force` перекачивает всё).
3. Иначе условный GET → разбор → хеш содержимого (SHA-256 по структурированному тексту).
4. Хеш совпал → страница не тронута. Новая/изменилась → чанки статьи заменяются атомарно (транзакция) вместе с FTS-записями.
5. Эмбеддинги считаются **только для текстов, которых нет в кэше** (ключ — SHA-1 текста + модель); эмбеддинг заголовков — отдельным проходом. Изменение одной статьи не приводит к пересчёту остальных.
6. Страницы, исчезнувшие из sitemap и ссылок, удаляются вместе с чанками (если обнаружено < 50 % от числа проиндексированных — удаление блокируется как подозрительное). Временный сбой загрузки данные **не** удаляет.
7. Осиротевшие эмбеддинги удаляются; результат записывается в `sync_runs` и показывается на `/admin`.

Пример итога (повторный запуск без изменений на сайте):

```
Articles discovered: 339
Unchanged: 339
Updated: 0
New: 0
Removed: 0
Failed: 0
Chunks updated: 0
Embeddings computed: 0
HTTP requests: 1
Duration: 1.3s
```

Замеры на 4 vCPU: полный первый прогон — краулинг 4 мин, эмбеддинги чанков ≈ 29 мин (e5-large на CPU), эмбеддинги заголовков ≈ 4,5 мин. Поэтому готовый индекс лежит в репозитории.

## Ночная синхронизация (инструкция; планировщик в проект не входит)

Linux/macOS (cron, 03:15):
```
15 3 * * * cd /path/to/webim-ai-knowledge && .venv/bin/python -m webim_ai.sync >> data/sync.log 2>&1
```
Windows: Планировщик заданий → действие `C:\path\.venv\Scripts\python.exe -m webim_ai.sync`, рабочая папка — корень проекта. После синхронизации запущенный сервер подхватит новые данные при перезапуске (горячая перезагрузка индекса — в планах; сейчас `Retriever.reload()` есть, но не вызывается автоматически).

## Ограничения

* Индексируется текст; изображения не индексируются (подписи и `alt` — да), видео (`videoguides.html`) — только текст страницы.
* Якоря MkDocs (`#_2`) нестабильны при правках структуры статьи — это свойство исходного сайта.
* Автоматическое расписание и горячая перезагрузка индекса не реализованы.
