# Архитектура

```
webim.ru/kb ──► crawler ──► parser ──► chunker ──► SQLite (articles, chunks, FTS5, embeddings, sync_runs)
 (sitemap +        │           │           │                        │
  ссылки)      кэш+ETag   секции/якоря  чанки с путём          ┌────┴─────────────────────────────┐
                                        заголовков и якорем    │ retrieval: lexical + semantic +   │
вопрос ─► FastAPI ─────────────────────────────────────────────►  heading-semantic → RRF → rerank  │
                                                               └────┬─────────────────────────────┘
                         SSE: retrieval → token* → final            ▼
        web UI ◄────────────────────────────────────  answer: LLM (OpenAI-compatible / Anthropic)
                                                          или извлекающий ответ; проверка цитат
```

Одно приложение (Python), один файл БД (SQLite), без отдельных сервисов. Интерфейс — статические файлы, отдаются тем же сервером.

## Данные и provenance

Каждый чанк хранит: `url`, `anchor` (id заголовка), `heading_path` (H1 › H2 › H3), `title`, `text`; статья — хлебные крошки, дату обновления, хеш содержимого и полную структуру (для обзора). Ссылка на источник строится как `url#anchor` и проверяется: `eval/check_links.py` подтверждает, что якорь каждого из 4 883 чанков существует в HTML страницы. Provenance проходит без потерь: парсер → чанк → индекс → кандидаты → реранкер → `evidence` → цитата `[n]` → карточка источника в UI.

Особенность сайта: MkDocs Material генерирует якоря вида `#_2` (кириллические заголовки не транслитерируются). Они стабильны в пределах версии страницы, но могут сдвинуться, если авторы добавят раздел выше; ночная синхронизация обновляет якоря вместе с текстом.

## Разбиение (chunker.py)

Чанк = раздел (заголовок + собственное содержимое). Пустые разделы отбрасываются (заголовок остаётся в пути потомков); раздел короче 110 символов вместе со следующим подразделом образует один чанк с якорем подраздела; раздел длиннее ~1100–1600 символов режется по границам блоков (абзац, пункт списка, строка кода), путь заголовков повторяется в каждой части. Код, таблицы и списки сохраняются как текст. Версия правил (`CHUNKER_VERSION`) записывается в индекс: при её изменении чанки пересобираются из сохранённых статей без обращения к сети.

## Поиск (retrieval.py)

1. **Лексика.** SQLite FTS5, поля `title / headings / body` (веса 6/4/1) по **стеммам** (Snowball ru/en; идентификаторы `password_hashers`, `webimsdk.onBan`, camelCase дают и целое, и части).
2. **Семантика чанков.** `multilingual-e5-large` (1024-мерные векторы, ONNX Runtime на CPU; префиксы `query:`/`passage:`), косинус по матрице в памяти (4 883 × 1024, float16 в БД).
3. **Семантика заголовков.** Отдельные короткие эмбеддинги «Статья › Раздел» — сигнал для вопросов, которые звучат как название темы. Добавлен после первой оценки: hit@3 гибрида вырос с 85 % до 88 %, MRR с реранкером с 0,84 до 0,88.
4. **Слияние.** Reciprocal Rank Fusion (k = 60; веса 1 / 1 / 0,8) — устойчиво к разным шкалам оценок.
5. **Реранкер.** `bge-reranker-v2-m3` (int8 ONNX) перепроверяет 20 лучших кандидатов пары (вопрос, «заголовок + текст»), обрезка 320 токенов.
6. **Доказательства.** Лучший чанк берётся всегда, остальные — если оценка ≥ max(0,05; 0,25 × лучшая); не более 2 чанков на статью, не более 5 в ответ. Список «Релевантные статьи» строится отдельно и не зависит от генерации.

Модули заменяемы: `EMBED_MODEL` / `RERANK_MODEL` (реестр в `models.py`; новая модель = запись `ModelSpec`), эмбеддинги кэшируются по хешу текста и имени модели.

### Уверенность и отказ

Ответ выдаётся, только если лучший чанк «уверенный»: оценка реранкера ≥ 0,12, либо ≥ 0,05 при независимом подтверждении (1–2-е место в лексике, 1-е в семантике или по заголовку). Дополнительно: если в вопросе есть название (латиницей, с заглавной буквы не в начале фразы или с цифрой), которого **нет нигде в индексе** (Bitrix24, Signal), система отказывается отвечать и говорит об этом. Пороги подобраны по `eval/questions.json` — см. оговорки в `FINAL_REPORT.md`. Без реранкера/семантики работает запасной режим (покрытие слов запроса).

## Ответ (answer.py)

* `build_messages`: системный промпт (документация — данные, не инструкции; только факты из источников; точный текст отказа; цитаты `[n]`), затем блоки `<source id="n" article=… section=… path=…>` с очищенным текстом. Из текста удаляются теги `<source>` и строки, похожие на инъекцию («ignore previous instructions» и т. п.).
* Провайдеры: `OpenAICompatible` (стриминг SSE, скрывает `<think>…</think>`), `AnthropicProvider`. Выбор — `.env`.
* После генерации `validate_citations` удаляет ссылки на несуществующие источники; ответ «недостаточно информации» от модели трактуется как отказ.
* Нет LLM или он недоступен → `extractive_answer`: лучшие предложения лучших фрагментов (по совпадению стеммов), каждое со ссылкой `[n]`, ничего не генерируется.
* Если retrieval не уверен — LLM **не вызывается вообще**.

## Интерфейс (web/)

Ванильный JS без сборки. Роутинг через History API (`/`, `/browse`, `/demo`, `/admin`). Весь пользовательский и документный текст экранируется (`esc`) — в DOM попадает только текст, HTML документации не выполняется. Ответ стримится по SSE (`retrieval` → `token` → `final`). Дизайн-система выведена из webim.ru/kb: градиент `#313098 → #4ac7e3`, бирюзовые кнопки `#0d7791`, тёмно-синий `#14284d`, пилюли 30 px, карточки 14 px, Roboto (файлы шрифтов — те же, что использует KB).

## Производительность (4 vCPU, без GPU)

Лексика — единицы–десятки мс, эмбеддинг запроса ≈ 80 мс, семантика ≈ 90 мс, слияние < 1 мс, **реранкер ≈ 2,5 с** (20 пар × 320 токенов на CPU) — основная часть задержки. На современном настольном CPU/GPU (`onnxruntime-gpu`/DirectML/CoreML, `ORT_USE_GPU=1`) ожидается существенно быстрее (не измерялось). Уменьшить: `RERANK_CANDIDATES=12` (≈ −30 % времени, MRR 0,89 вместо 0,90). Диагностика по запросам — на `/admin` и в `?debug=1`.
